Ollama API key: your local Ollama doesn't have one. Here's how to require one

By MV2 of Munim, Inc. Checked against the Ollama authentication docs, the Ollama FAQ, the n8n Ollama credential docs, the Open WebUI API docs and the Caddy matcher docs on 12 October 2026. For your own machines only.

The short answer

  • OLLAMA_API_KEY is for ollama.com, Ollama's cloud. You create it in your ollama.com settings and send it to https://ollama.com/api. It doesn't protect your own server.
  • Your own Ollama has no login. Ollama's docs say: "The local API at http://localhost:11434 does not require authentication." There's no setting that turns one on. Anyone who can reach port 11434 can run prompts on your GPU and pull, create or delete models.
  • To require a key, put a gate in front: keep Ollama on 127.0.0.1 and let a reverse proxy that checks an Authorization: Bearer <key> header be the only way in. That header is what OpenAI-style clients, n8n and Open WebUI send when you fill in an "API key" field.

If Ollama is only used on the machine it runs on, you don't need any of this. Leave it on 127.0.0.1; the lock-down checklist shows how to confirm it.

Option A: already running Open WebUI? Use it as the gate

Open WebUI passes requests through to Ollama under /ollama/, and it checks its own API keys. Ollama stays internal, and you don't need extra software.

  1. Create a key in Open WebUI under Settings > Account (keys start with sk-). If you don't see the option, an admin has to allow API keys first; see Open WebUI's API key docs.
  2. Call Ollama's native API through Open WebUI: 
    curl https://webui.example.home/ollama/api/tags -H "Authorization: Bearer sk-..."
    or use Open WebUI's OpenAI-compatible endpoint, /api/chat/completions.
  3. In n8n, set the Ollama credential's Base URL to https://webui.example.home/ollama and its API Key to the sk- key. n8n's docs name Open WebUI as an example of this setup.

The key carries that Open WebUI user's permissions, so make a separate user for each app, and keep Open WebUI updated (see Open WebUI advisories).

Option B: a small proxy that checks a key

1. Keep Ollama local and make a key

Ollama must listen on 127.0.0.1:11434 (the default). If you set OLLAMA_HOST=0.0.0.0 earlier, undo it as in step 2 of the checklist. If you don't, people can skip the proxy by going straight to port 11434. Then generate a long random key:

openssl rand -hex 32
# or
python3 -c "import secrets; print(secrets.token_urlsafe(32))"

2a. Caddy

Caddy gets an HTTPS certificate on its own when ollama.example.com is a real domain that points at this machine. Replace the domain and PASTE_YOUR_KEY_HERE:

ollama.example.com {
    @key header Authorization "Bearer PASTE_YOUR_KEY_HERE"
    handle @key {
        reverse_proxy 127.0.0.1:11434 {
            header_up Host localhost:11434
            header_up -Authorization
        }
    }
    handle {
        respond "Missing or wrong API key" 401
    }
}
  • The header matcher is an exact match, so only Bearer, one space and your exact key gets through. To give each person or app its own key, add more header Authorization "Bearer ..." lines in a @key { ... } block. Caddy ORs values of the same header.
  • header_up Host localhost:11434 follows the Ollama FAQ's proxy example; Ollama can refuse requests that arrive with other Host values. header_up -Authorization keeps your key from being passed on to Ollama.
  • If streamed answers arrive all at once, add flush_interval -1 inside the reverse_proxy block.
  • The file now holds a secret. Make it readable only by root and Caddy, then reload: sudo chown root:caddy /etc/caddy/Caddyfile && sudo chmod 640 /etc/caddy/Caddyfile && sudo systemctl reload caddy

LAN-only name (such as ollama.home): there's no public certificate, so use tls internal inside the site block and install Caddy's root certificate on your clients. Or skip the proxy and use a private network such as Tailscale or WireGuard. Don't send the key over plain http:// on a network you don't trust; anyone on that network could read it.

2b. nginx

Put this in /etc/nginx/conf.d/ollama.conf. Files in conf.d are read inside the http block, where map belongs. Use your own certificate paths, for example from certbot:

map $http_authorization $ollama_key_ok {
    default                        0;
    "Bearer PASTE_YOUR_KEY_HERE"   1;
}

server {
    listen 443 ssl;
    server_name ollama.example.com;
    ssl_certificate     /etc/letsencrypt/live/ollama.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ollama.example.com/privkey.pem;

    location / {
        if ($ollama_key_ok = 0) { return 401; }
        proxy_pass http://127.0.0.1:11434;
        proxy_set_header Host localhost:11434;
        proxy_set_header Authorization "";   # don't pass the key on to Ollama
        proxy_buffering off;                 # stream tokens as they come
        proxy_read_timeout 600s;             # long generations
        client_max_body_size 0;              # model uploads (ollama create)
    }
}

Add one line to the map for each extra key. Then run sudo nginx -t && sudo systemctl reload nginx, and make the file readable only by root (sudo chmod 600 /etc/nginx/conf.d/ollama.conf; nginx reads it as root at startup).

2c. Ollama in Docker

Give the ollama service no ports: at all and publish only Caddy. In the Caddyfile above, use reverse_proxy ollama:11434. Add your usual GPU settings to the ollama service.

services:
  ollama:
    image: ollama/ollama
    volumes: [ "ollama:/root/.ollama" ]
    # no "ports:" - only containers on this network can reach it
  caddy:
    image: caddy:2
    ports: [ "80:80", "443:443" ]
    volumes: [ "./Caddyfile:/etc/caddy/Caddyfile:ro", "caddy_data:/data" ]
volumes:
  ollama: {}
  caddy_data: {}

3. Test it

# no key: should print 401
curl -s -o /dev/null -w "%{http_code}\n" https://ollama.example.com/api/version

# with the key: should print {"version":"..."}
curl -H "Authorization: Bearer YOUR_KEY" https://ollama.example.com/api/version

# from ANOTHER machine, straight to Ollama: should fail to connect
curl http://<server LAN IP>:11434/api/version

If the last command answers with a version, the proxy can be bypassed. Check OLLAMA_HOST and Docker ports: again. On Linux, ufw doesn't block ports that Docker publishes.

Connect your apps

  • Open WebUI on another machine: Admin Panel > Settings > Connections. Add or edit the Ollama API connection, set the URL to https://ollama.example.com, and put the key in its Key field (sent as a Bearer token). If your version has no Key field for Ollama connections, add it as an OpenAI API connection with the URL https://ollama.example.com/v1 and the key instead.
  • n8n: in the Ollama credential, set Base URL to https://ollama.example.com and API Key to your key. n8n sends it as Authorization: Bearer.
  • OpenAI SDK and OpenAI-compatible tools (Continue, LibreChat and others): set the base URL to https://ollama.example.com/v1 and the API key to your key. 
    from openai import OpenAI
client = OpenAI(base_url="https://ollama.example.com/v1", api_key="YOUR_KEY")
reply = client.chat.completions.create(
    model="llama3.2", messages=[{"role": "user", "content": "Hello"}])
print(reply.choices[0].message.content)
  • The ollama Python library: pass the header yourself. 
    from ollama import Client
client = Client(host="https://ollama.example.com",
                headers={"Authorization": "Bearer YOUR_KEY"})
print(client.list())
  • The ollama command: as of this check there's no documented way to make it send your own key to a custom host. Run it on the server itself, or use curl or the libraries above.

Mistakes to avoid

  • The proxy is in place, but port 11434 is still open. The key only helps if the proxy is the only way in; run the third test above.
  • Basic auth for API clients. The Caddy basic_auth example in the checklist works for browsers and curl -u, but OpenAI-style clients, n8n and Open WebUI send Authorization: Bearer, so basic auth rejects them. Use the key check on this page for API clients.
  • The key in a web page. Anything in browser JavaScript can be read by whoever loads the page. Keep keys on servers and in app settings, and keep OLLAMA_ORIGINS narrow (browser check).
  • Treating the key as the whole fix. Anyone with the key still reaches every endpoint, including the ones this year's CVEs were in. Keep Ollama updated (Ollama CVEs, or type your version into the CVE checker). Change the key by editing the config and reloading the proxy.
