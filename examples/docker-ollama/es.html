Open WebUI o n8n en Docker no se conectan a Ollama

Por MV2 de Munim, Inc. Comprobado el 12 de octubre de 2026 con la documentación de Open WebUI y n8n y el código fuente de Ollama. Esta página se tradujo con IA del original en inglés; si hay diferencias, prevalece el original.

Errores típicos: Open WebUI muestra «Ollama: Network Problem» o «Server Connection Error», o sus registros dicen Connect call failed ('127.0.0.1', 11434). La prueba de la credencial de Ollama en n8n falla con ECONNREFUSED 127.0.0.1:11434 o ECONNREFUSED ::1:11434. Dify, Flowise y AnythingLLM dan errores parecidos de «connection refused».

La causa: dentro de un contenedor, localhost y 127.0.0.1 son el propio contenedor, no su ordenador. Por defecto, Ollama escucha en 127.0.0.1:11434 en el host, así que un contenedor que usa http://localhost:11434 está llamando a la puerta equivocada.

El arreglo rápido que dan muchas guías es OLLAMA_HOST=0.0.0.0. Funciona, pero también abre Ollama, que no tiene inicio de sesión, a todos los dispositivos de su red. Pruebe antes las soluciones de abajo.

Primero, pruebe: un comando

Desde el host, compruebe que Ollama está activo: curl http://127.0.0.1:11434/api/version. Después pruebe la dirección que usa su aplicación desde dentro de un contenedor desechable:

docker run --rm --add-host=host.docker.internal:host-gateway curlimages/curl -s http://host.docker.internal:11434/api/version

Una respuesta como {"version":"0.x.y"} significa que esa URL funciona desde los contenedores. «Connection refused» o un tiempo de espera agotado significa que no; siga leyendo según su configuración. La imagen de Open WebUI incluye curl, así que también puede ejecutar docker exec open-webui curl -s http://host.docker.internal:11434/api/version.

Solución 1: Docker Desktop (Mac, Windows)

Docker Desktop ofrece host.docker.internal a todos los contenedores y lo redirige a su ordenador, así que defina la URL de Ollama de la aplicación como http://host.docker.internal:11434. En Open WebUI es la variable de entorno OLLAMA_BASE_URL (o «Admin Settings» → «Connections»). En n8n, edite la «Base URL» de la credencial de Ollama. No hace falta cambiar OLLAMA_HOST en Ollama.

docker run -d -p 127.0.0.1:3000:8080 --add-host=host.docker.internal:host-gateway \
  -e OLLAMA_BASE_URL=http://host.docker.internal:11434 \
  -v open-webui:/app/backend/data --name open-webui --restart always \
  ghcr.io/open-webui/open-webui:main

127.0.0.1:3000 limita Open WebUI a este ordenador. Use -p 3000:8080 solo si otros dispositivos deben abrirlo, y en ese caso desactive el registro abierto. Para usarlo desde el teléfono sin abrirlo a la red, vea Open WebUI con Tailscale Serve.

Solución 2: Linux, la forma segura más sencilla: red del host para la aplicación

En Linux, --network=host pone el contenedor en la red del host, de modo que 127.0.0.1:11434 es de verdad el Ollama del host y Ollama puede seguir enlazado a localhost. La documentación de Open WebUI da esta solución; tenga en cuenta que el puerto pasa a ser 8080:

docker run -d --network=host \
  -e OLLAMA_BASE_URL=http://127.0.0.1:11434 \
  -v open-webui:/app/backend/data --name open-webui --restart always \
  ghcr.io/open-webui/open-webui:main

Abra http://localhost:8080. Con la red del host, Open WebUI escucha en el puerto 8080 como un programa normal, y aquí el cortafuegos del host (ufw, firewalld) sí se aplica. Permita el 8080 solo desde donde lo necesite.

Solución 3: Linux, host.docker.internal con Ollama accesible solo desde contenedores

En Linux, --add-host=host.docker.internal:host-gateway (o extra_hosts: ["host.docker.internal:host-gateway"] en Compose) apunta ese nombre a la dirección del puente de Docker, normalmente 172.17.0.1. Ollama en 127.0.0.1 no escucha ahí, así que tiene que escuchar de forma más amplia, y un cortafuegos debe dejar fuera a todos salvo a los contenedores:

  1. Haga que Ollama escuche en todas las interfaces: sudo systemctl edit ollama.service, añada 
    [Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
    y después sudo systemctl daemon-reload && sudo systemctl restart ollama.
  2. Permita solo las redes de Docker y bloquee el resto (ejemplo con ufw; las redes por defecto de Docker están en 172.16.0.0/12): 
    sudo ufw allow from 172.16.0.0/12 to any port 11434 proto tcp
sudo ufw deny 11434/tcp
    El orden importa: la regla allow debe ir primero (sudo ufw status numbered muestra el orden). Si ufw está activo con su «deny incoming» por defecto, la regla allow es lo único que deja entrar a los contenedores. Un contenedor bloqueado suele ver un tiempo de espera agotado en lugar de «refused».
  3. Desde otro dispositivo de su red, curl http://<this machine's LAN IP>:11434/api/version (con la IP de esta máquina en la red local) debería fallar ahora, mientras que la prueba del contenedor desechable de arriba funciona.

A diferencia de los puertos publicados con docker -p, que se saltan ufw, Ollama instalado en el host es un programa normal, así que estas reglas de ufw sí se le aplican.

Solución 4: ponga Ollama en el mismo archivo Compose

Los contenedores de la misma red de Compose se alcanzan por el nombre del servicio, así que Ollama no necesita puerto publicado y nada fuera de Docker puede llegar a él:

services:
  ollama:
    image: ollama/ollama
    volumes: [ "ollama:/root/.ollama" ]
    # no "ports:" - only containers on this network can reach it
  open-webui:
    image: ghcr.io/open-webui/open-webui:main
    environment:
      - OLLAMA_BASE_URL=http://ollama:11434
    ports: [ "127.0.0.1:3000:8080" ]
    volumes: [ "open-webui:/app/backend/data" ]
volumes:
  ollama: {}
  open-webui: {}

(El comentario del archivo dice: sin «ports:», solo los contenedores de esta red pueden alcanzarlo.) n8n, Dify, Flowise o AnythingLLM en el mismo archivo también usan http://ollama:11434. Para una GPU, añada al servicio ollama la reserva de dispositivos de la documentación de Docker de Ollama. Si la aplicación está en otro proyecto de Compose, conecte ambos a una misma red externa compartida.

¿Sigue fallando?

  • n8n en el host, ECONNREFUSED ::1:11434: localhost se resolvió a IPv6 y Ollama escucha en IPv4. La documentación de n8n sugiere 127.0.0.1 en lugar de localhost.
  • Podman: el nombre del host es host.containers.internal.
  • «403 Forbidden» en vez de «refused»: no es un problema de red: Ollama respondió y dijo que no. Hay dos causas habituales. (1) Una página web o una extensión del navegador llama a Ollama y OLLAMA_ORIGINS la bloquea; vea la comprobación del navegador (en inglés). Open WebUI, n8n y Dify llaman a Ollama desde su servidor y no necesitan OLLAMA_ORIGINS. (2) Un proxy inverso o un túnel pasa su propio nombre de host a un Ollama que escucha en 127.0.0.1. En ese modo Ollama solo acepta nombres de Host del estilo de localhost; por eso funciona host.docker.internal (termina en .internal). Haga que el proxy envíe Host: localhost:11434, como hacen los ejemplos de las preguntas frecuentes de Ollama. Tailscale Serve choca con la misma comprobación; vea por qué tailscale serve devuelve 403.
  • Funciona, pero lento: vea Ollama slow or not using the GPU (en inglés).
