Open WebUI or n8n in Docker can't connect to Ollama

By MV2 of Munim, Inc. Checked against the Open WebUI and n8n docs and Ollama's source on 12 October 2026.

Typical errors: Open WebUI shows "Ollama: Network Problem" or "Server Connection Error", or its logs say Connect call failed ('127.0.0.1', 11434). n8n's Ollama credential test fails with ECONNREFUSED 127.0.0.1:11434 or ECONNREFUSED ::1:11434. Dify, Flowise and AnythingLLM give similar "connection refused" errors.

The cause: inside a container, localhost and 127.0.0.1 mean the container itself, not your computer. Ollama listens on 127.0.0.1:11434 on the host by default, so a container using http://localhost:11434 is knocking on the wrong door.

The quick fix many guides give is OLLAMA_HOST=0.0.0.0. It works, but it also opens Ollama, which has no login, to every device on your network. Try the fixes below first.

Test first: one command

From the host, check Ollama is up: curl http://127.0.0.1:11434/api/version. Then test the address your app uses from inside a throwaway container:

docker run --rm --add-host=host.docker.internal:host-gateway curlimages/curl -s http://host.docker.internal:11434/api/version

A reply like {"version":"0.x.y"} means that URL works from containers. "Connection refused" or a timeout means it doesn't; read on for your setup. Open WebUI's image includes curl, so you can also run docker exec open-webui curl -s http://host.docker.internal:11434/api/version.

Fix 1: Docker Desktop (Mac, Windows)

Docker Desktop provides host.docker.internal to every container and forwards it to your computer, so set the app's Ollama URL to http://host.docker.internal:11434. For Open WebUI that's the environment variable OLLAMA_BASE_URL (or Admin Settings, Connections). In n8n, edit the Ollama credential's Base URL. Ollama doesn't need OLLAMA_HOST changed.

docker run -d -p 127.0.0.1:3000:8080 --add-host=host.docker.internal:host-gateway \
  -e OLLAMA_BASE_URL=http://host.docker.internal:11434 \
  -v open-webui:/app/backend/data --name open-webui --restart always \
  ghcr.io/open-webui/open-webui:main

127.0.0.1:3000 keeps Open WebUI to this computer. Use -p 3000:8080 only if other devices should open it, and then turn off open sign-ups. To reach it from your phone without opening it to the network, see Open WebUI over Tailscale Serve.

Fix 2: Linux, the simplest safe way: host networking for the app

On Linux, --network=host puts the container on the host's network, so 127.0.0.1:11434 really is the host's Ollama and Ollama can stay bound to localhost. Open WebUI's docs give this fix; note the port becomes 8080:

docker run -d --network=host \
  -e OLLAMA_BASE_URL=http://127.0.0.1:11434 \
  -v open-webui:/app/backend/data --name open-webui --restart always \
  ghcr.io/open-webui/open-webui:main

Open http://localhost:8080. With host networking, Open WebUI listens on port 8080 like a normal program, and here your host firewall (ufw, firewalld) does apply. Allow 8080 only from where you need it.

Fix 3: Linux, host.docker.internal with Ollama reachable only from containers

On Linux, --add-host=host.docker.internal:host-gateway (or extra_hosts: ["host.docker.internal:host-gateway"] in Compose) points that name at the Docker bridge address, usually 172.17.0.1. Ollama on 127.0.0.1 doesn't listen there, so it has to listen more widely, and a firewall must keep everyone except containers out:

  1. Make Ollama listen on all interfaces: sudo systemctl edit ollama.service, add 
    [Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
    then sudo systemctl daemon-reload && sudo systemctl restart ollama.
  2. Allow only Docker's networks, then block the rest (ufw example; Docker's default networks are in 172.16.0.0/12): 
    sudo ufw allow from 172.16.0.0/12 to any port 11434 proto tcp
sudo ufw deny 11434/tcp
    Order matters: the allow rule must come first (sudo ufw status numbered shows the order). If ufw is on with its default "deny incoming", the allow rule is what lets containers in at all. A blocked container usually sees a timeout rather than "refused".
  3. From another device on your network, curl http://<this machine's LAN IP>:11434/api/version should now fail, while the throwaway-container test above succeeds.

Unlike ports published with docker -p, which skip ufw, Ollama installed on the host is a normal program, so these ufw rules do apply to it.

Fix 4: put Ollama in the same Compose file

Containers on the same Compose network reach each other by service name, so Ollama needs no published port and nothing outside Docker can reach it:

services:
  ollama:
    image: ollama/ollama
    volumes: [ "ollama:/root/.ollama" ]
    # no "ports:" - only containers on this network can reach it
  open-webui:
    image: ghcr.io/open-webui/open-webui:main
    environment:
      - OLLAMA_BASE_URL=http://ollama:11434
    ports: [ "127.0.0.1:3000:8080" ]
    volumes: [ "open-webui:/app/backend/data" ]
volumes:
  ollama: {}
  open-webui: {}

n8n, Dify, Flowise or AnythingLLM in the same file use http://ollama:11434 too. For a GPU, add the device reservation from the Ollama Docker docs to the ollama service. If the app runs in a different Compose project, attach both to one shared external network.

Still failing?

  • n8n on the host, ECONNREFUSED ::1:11434: localhost resolved to IPv6 and Ollama listens on IPv4. n8n's docs suggest 127.0.0.1 instead of localhost.
  • Podman: the host name is host.containers.internal.
  • "403 Forbidden" rather than refused: that's not networking: Ollama answered and said no. There are two usual causes. (1) A browser page or extension is calling Ollama and OLLAMA_ORIGINS blocks it; see the browser check. Open WebUI, n8n and Dify call Ollama from their server and don't need OLLAMA_ORIGINS. (2) A reverse proxy or tunnel passes its own hostname to an Ollama listening on 127.0.0.1. In that mode Ollama accepts only localhost-style Host names, which is why host.docker.internal works (it ends in .internal). Have the proxy send Host: localhost:11434, as the Ollama FAQ's examples do. Tailscale Serve hits the same check; see why tailscale serve returns 403.
  • Works, but slow: see Ollama slow or not using the GPU.
